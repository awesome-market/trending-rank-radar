🚀 Web Frameworks Benchmark

A community-maintained, reproducible comparison of backend web frameworks

Explore the results · Add a framework · Report a problem · Join the discussion








From established full-stack platforms to small HTTP routers, this repository puts hundreds of implementations behind the same tiny API and runs them in isolated containers. Today, it makes a focused part of web-stack performance easier to measure, reproduce, and discuss. The longer-term goal is a comprehensive, evidence-based guide that helps businesses choose a backend framework—not merely a leaderboard that declares one universal winner.

 [!IMPORTANT]
 These are minimal HTTP throughput and latency tests, not a substitute for profiling a production application. Framework features, maintainability, ecosystem, security, database access, and your real workload all matter.

 🧪 Benchmark contract

Framework submissions must implement the v2 benchmark contract. V1 submissions are no longer accepted.

Every implementation listens on port 3000. Existing v1 implementations use these legacy routes:

| Method | Route | Expected status | Expected body |
|:--|:--|:--:|:--|
| GET | / | 2xx | Empty |
| GET | /user/:id | 2xx | The id path parameter |
| POST | /user | 2xx | Empty |

Before a v1 implementation is benchmarked, the shared Gherkin contract verifies these routes. The default v1 benchmark runs all three routes for 15 seconds each using zrk --closed and keep-alive, and records JSON reports. Concurrency and routes are configurable.

 Migrating an implementation to v2

V2 is the default contract. At this revision, 16 of 442 framework
implementations use v2 and 426 still select v1 in their framework
config.yaml files. To migrate a v1 implementation:

1. Update the app to implement the six routes and validation rules in the
   v2 scenario. In particular, /user/{id} returns a JSON ID,
   and v2 adds JSON serialization, JSON deserialization, and multipart upload.
2. Remove the top-level specs: v1 line from its config.yaml. Omission selects
   v2; adding specs: v2 is unnecessary.
3. Regenerate its commands and run the full correctness suite:

   bash
   bundle exec rake config
   make -f //.Makefile test
   

The test target checks the selected v2 contract before benchmarking. The
generated default workloads then measure dynamic routing, JSON
serialization/deserialization, and multipart upload.

Each framework's config.yaml selects its contract with a top-level specs: v1
or specs: v2. Only the selected contract's tests and workloads run; omitting
specs defaults to v2. Rails selects the four-workload
v2 scenario: routing, JSON serialization/deserialization, and
multipart uploads. Generate the commands before building the implementation:

bash
bundle exec rake config
make -f ruby/rails/.Makefile build
make -f ruby/rails/.Makefile test
