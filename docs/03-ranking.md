# 03 榜单算法与历史回看

> 口径经同类 GitHub 榜单站公开数据的实测逆向校准（2026-11-08）。

## 核心机制：每日 Star 时间序列 + 差值

每个跟踪仓库维护**每日指标序列**（按北京时间自然日归并，保留全部历史）：

```
daily_metrics[repo] = {
  "2026-10-17": {stars, forks, watchers, ...},
  "2026-10-18": {stars, forks, watchers, ...},
  ...
}
```

所有榜单都从序列差分得出，不依赖 GitHub 的 Trending 排名。

## 十一种榜单

记号：`S(repo, D)` = 仓库在**北京时间自然日 D 的收盘快照**（当天最后一次运行）的 Star 数。所有窗口以 CST 日界为准，与 UTC 快照时间戳无关。

| type | 榜单 | 口径 | 数据前提 |
|---|---|---|---|
| 1 | 新榜 new | `created_at` 在最近 **90 天**内，按当前 Star 降序 | 需 created_at |
| 1b | 首登榜 debut | **首次进入任一榜单**的仓库（该日之前从未在任何榜的 items 中出现），按日窗口增长降序；无可用基点的按 Star 排尾 | ≥2 个有效日 |
| 2 | 日飙升榜 daily | `S(D) − S(D−1)` 降序 | ≥2 个有效日 |
| 3 | 日增速榜 daily_rate | `日增量 / (S(D) − 日增量) × 100` 降序（百分比，向下取整） | ≥2 个有效日 |
| 4 | 周飙升榜 weekly | `S(D) − S(D−7)` 降序 | 窗口按可用历史回退（见下） |
| 5 | 周增速榜 weekly_rate | `周增量 / (S(D) − 周增量) × 100` 降序 | 同上 |
| 6 | 月飙升榜 monthly | `S(D) − S(D−30)` 降序 | 同上 |
| 7 | 月增速榜 monthly_rate | `月增量 / (S(D) − 月增量) × 100` 降序 | 同上 |
| 8 | 总榜 total | 当前 Star 总数降序 | 仅需最新快照 |
| 9 | Fork 日增榜 daily_forks | `F(D) − F(基点)` 降序（Fork 计数） | 同日榜窗口规则 |
| 10 | Watch 日增榜 daily_watchers | `W(D) − W(基点)` 降序（Watchers 计数） | 同上；watchers 为扩展字段，榜单较稀 |

### 窗口回退规则

窗口起点早于项目首个快照时，**用最早可用快照作基数**，增量按实际可用天数计算（同类榜单站实测亦如此——月增字段实为 24 天差分）。前端在"统计时间"处显示**实际区间**（如 `10-15 ~ 11-08（24天）`），避免误导。

由此冷启动期各榜单即可用：上线第 2 天日榜可出，周/月榜以"近 N 天"口径先行展示，窗口逐渐补满后自动变为完整 7/30 天口径。

### 增速公式（实测验证）

```
增速% = 增长量 / 窗口起点Star基数 × 100
      = incr / (S(D) − incr) × 100     // 分母恒等于窗口起点 Star 数
```

- 结果**向下取整**为整数百分比
- **除零保护**：基数 < 50 的仓库不参与增速榜（过滤规则已含，此处强调顺序：先过滤再计算）

验证样本（外部真实数据）：
- `storytold/craft-anything`：日增 3836 / 基数 3896 → **98%** ✓
- `cn-math-taxonomy`：周增 2353 / 基数 4015 → 58.58% → **58** ✓

### 新榜口径

`created_at` 在最近 **90 天**内（滚动窗口，持续有新内容），当前 Star ≥ 20，按 Star 降序。
> 同类站点新榜按"YYYY年"展示；我们采用 90 天滚动窗——在 ~2000 仓库的 watchlist 规模下，"当年"候选池过大且头部固化，90 天更能持续刷新。
> **覆盖度说明**：候选来自 Search API（单查询上限 1000 条，按 Star 截断）+ Trending，故新榜是"高关注度新仓库"子集而非全量新仓库——README/页脚需注明口径，避免误导。

### 过滤规则

- 排除 `is_fork`、`is_archived` 仓库
- 增长榜（type 2–7）：窗口增量 > 0 且当前 Star ≥ 100
- 指标榜（type 9–10）：对应计数窗口增量 > 0；当前 Star 下限沿用 100（指标榜展示的是这些仓库的非 Star 增长）
- 增速榜额外要求：基数 ≥ 50（避免小基数产生 9999% 的荒谬值）
- **预计算每榜 Top 200**（而非 Top 100）：前端 Star 范围筛选（k 为单位，`currentStarNum ∈ [min×1000, max×1000]`，默认 1–500）在 Top 200 内过滤后取 Top 100 展示，给筛选留出余量
- 仓库级数据缺失（窗口起点无快照）：用最早可用快照作基数，条目标记 `approx: true`，UI 显示 `≈`

### 快照缺失处理

- 当日某次运行失败：`rank.py` 取该 CST 日**最后一次成功**快照作为收盘值；若当天完全无快照，该日无榜单（`index.json.dates` 不含此日）
- 仓库当日缺失（拉取失败/被删）：沿用其最近一次成功快照值，并标记 `stale: true`，增量按 0 处理不进榜

## 历史回看语义

### 按日查看

选日期 `D` → 展示 `D` 当天九榜（以 `D` 为"today"重算窗口，窗口按当时可用历史回退）。数据：`site/data/days/YYYY-MM-DD.json`。

### 按月查看

选 `YYYY-MM` → 展示：

1. **月末九榜快照**：该月最后一个有效快照日的榜单
2. **当月累计增长榜**：`S(月末) − S(月初首个快照日)` 降序（进行中的月份标注"截至今日"）
3. **当月每日 Top10 摘要**

数据：`site/data/months/YYYY-MM.json`。

### 按年查看

选 `YYYY` → 展示：

1. **年度增长榜**：`S(年末) − S(年初)`，区间不足一年的按实际可用区间计算并标注
2. **年度月度榜**：12 个月各自的月榜入口

数据：`site/data/years/YYYY.json`。

### 预计算策略

`rank.py` 遍历所有**有效快照日**重算（按 CST 日归并后，天数 ≈ 运行次数的一半，重算成本可忽略）：

```
site/data/
  index.json                    # 可用日期/月份/年份、有效快照天数、generated_at、langs
  days/YYYY-MM-DD.json          # 每日十一榜（Top200/榜）
  months/YYYY-MM.json           # 月视图聚合
  years/YYYY.json               # 年视图聚合
  langs/<slug>.json             # 最新日按语言重排的榜（候选池先按语言过滤再排名）
```

另有按语言静态页 `langs/<slug>.html`（日视图，复用主页 UI 的 `data-lang` 模式）与 `feed.xml`（Atom：最新日首登榜 + 日飙升榜 Top）。语言页生成条件：该语言跟踪仓库 ≥ 50 个，最多取前 15 种语言。

前端只读 JSON，不做计算。**体积估算**：每条目含 `series`（≤30 个数字）约 250B，Top200×8 榜去重后约 300–400 个唯一仓库 → 单日文件 ~100KB，年增 ~36MB，Pages 1GB 限额内可支撑 10+ 年。

## 指标扩展

快照已存 `stars / forks / watchers / issues_total / prs_total / releases_total`。注意 GitHub 语义差异：**REST 的 `open_issues_count` 同时含 issue 和 PR**；GraphQL 中 `issues` 与 `pullRequests` 是两个独立 connection，分开计数（本项目用 GraphQL，故两列分开）。前端元信息行对非 null 字段展示图标计数；后续可加"按 Forks/Watchers 增长排"维度。
